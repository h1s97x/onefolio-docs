# 部署边界与容量

这一页是**约束清单**。超出边界的能力不是「加个副本」就能得到，而是需要先改造存储、调度与状态三件事。

## 1. 单副本

| 边界     | 具体表现                                                                         |
| -------- | -------------------------------------------------------------------------------- |
| 文件存储 | 生成文件与导出包落本地磁盘（`STORAGE_DIR` / `EXPORT_DIR`），实例即数据           |
| 内存状态 | 节点并发上限缓存、节点故障隔离计数、SSO 一次性票据、批量调度互斥锁都在进程内存中 |
| 限流     | 应用层计数（RPC 失败时降级），多副本会各算一份                                   |

后果：直接 `--scale` 多副本会出现 **文件读不到 + 限流失真 + 故障节点仍被别的副本选中 + SSO 回调落到另一副本失败**。

::: warning 结论
**禁止横向扩容多副本。** 确需更高可用，请先完成：共享存储（对象存储或 NFS）、调度单实例化、内存状态外移（Redis / 数据库）、SSO 票据落库。
:::

## 2. 必须长驻进程

批量生成的推进依赖三处触发，全部要求 Node 进程存活：

| 触发点                        | 实现                                  | 生命周期         |
| ----------------------------- | ------------------------------------- | ---------------- |
| `start` / `resume` 后的长循环 | 批次调度服务                          | 进程存活期间持续 |
| 30 秒自愈定时器               | 应用启动时的 tick                     | 进程存活期间持续 |
| 外部定时任务兜底              | `POST /api/system/batch-tick`（超管） | 每次请求         |

| 部署形态                                | 是否满足  |
| --------------------------------------- | --------- |
| Docker / PM2 / 常驻 `next start`        | ✅        |
| 按请求计费、实例可随时回收的 Serverless | ⚠️ 不保证 |

不满足前提的表现：批次停在「生成中」不动 → 30 分钟后失联任务被回收机制**误标为失败**（文案「任务执行中断」）→ 用户看到"又报错了"。

Serverless 形态的补救：配置平台定时任务，每 1 分钟打一次 `POST /api/system/batch-tick`。

## 3. 并发上限怎么算

并发闸保护的是**智能体容量**，不是「每人能提交几个」。计算口径：**按报告类型分别计数**。

```text
某类型的并发上限 = Σ （承接该类型的已启用节点 concurrency）
```

- 未配置任何节点：回退环境变量单节点形态，兜底上限为 **2**；
- 该类型没有任何节点承接：提交时明确失败并提示，**不会**跨类型回落；
- 它是**软限制**：容量检查与任务写入不在同一事务，极小概率短暂超出上限 1~2 条。

::: tip 批量吞吐
批量单批并发默认 3，tick 间隔 30 秒，单批次约 **6 任务/分钟**（Agent 调用是 IO 等待）。662 家企业单批次串行约 **110 分钟**。

需要更快时先看智能体侧能不能扛：调大批次并发建议不超过 5（单节点场景）。
:::

## 4. 数据与权限边界

### 权限在应用层

数据库已启用 RLS 并回收 `anon` 全部表权限，但 `service_role` 具备 `BYPASSRLS`——应用**必须**用服务端密钥访问。

因此行级权限（本人 / 本机构 / 全量）由应用层实施，RLS 只拦住「绕过应用直连 PostgREST」这条路径。

::: danger 隐含假设
**只有应用进程访问数据库。** 任何直连数据库的脚本、BI 工具、人工 SQL 操作都在权限模型之外，请自行约束。
:::

### 表结构唯一来源

表结构的权威定义在应用代码（`src/lib/db/schema.ts`），`docker/initdb/01_schema.sql` 是它的可执行副本。结构变更后需重新生成该文件，否则**全新部署**会缺列。

已上线的库不走 `01_schema.sql`，而是按序号执行 `migrations/*.sql`。

## 5. 监控接什么

| 目标                                                | 端点 / 位置                            | 鉴权       |
| --------------------------------------------------- | -------------------------------------- | ---------- |
| 存活探活                                            | `HEAD /api/system/status`              | 匿名       |
| 存活摘要（含数据库与智能体状态）                    | `GET /api/system/status`               | 匿名       |
| 详细统计                                            | `GET /api/system/status?type=overview` | 管理员     |
| 节点级运行状态（在跑数 / 近 1 小时成败 / 隔离冷却） | `GET /api/system/agent-nodes`          | 管理员     |
| 批量调度兜底 tick                                   | `POST /api/system/batch-tick`          | 超级管理员 |

镜像内置 `HEALTHCHECK` 即调用 `HEAD /api/system/status`，可直接接入负载均衡或容器平台。

邮件告警：配置 `ALERT_EMAIL` 后，任务失败与系统级故障会发信给维护人。
